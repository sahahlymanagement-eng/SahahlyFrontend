# Sahahly ⇄ Mariam Gabalawy — grading integration

This document plus `Grading Partner API.postman_collection.json` are the complete integration spec. Read both.

## How the integration works

There are two directions, each with its own key.

| Direction | Who calls | Endpoint | Auth |
|---|---|---|---|
| **1. Submission notification** | You → Sahahly | `POST https://<SAHAHLY_API_BASE_URL>/api/grading/webhook` | `x-api-key: <webhook secret>` (we give you this) |
| **2. Pull submissions / push marks** | Sahahly → You | `GET /api/grading/submissions`, `GET /api/grading/submissions/{id}`, `POST /api/grading/submissions/{id}/marks` | `x-api-key: <your API key>` (you give us this) |

The flow: a student submits on your platform → you call our webhook → the submission appears in the Sahahly dashboard → we grade the submission → we `POST` the grade and an annotated PDF back to your `/marks` endpoint.

Direction 2 is specified entirely by the Postman collection. The rest of this document covers direction 1 and the requirements that span both.

## Key exchange

Neither key is in this document. Both are exchanged over a separate secure channel.

| Key | Generated by | Sent to | Used as |
|---|---|---|---|
| Webhook secret | **Sahahly** | You | The `x-api-key` you send on every webhook call |
| API key | **You** | Sahahly | The `x-api-key` we send on every call to your API |
| Base URL | **You** | Sahahly | Your origin, e.g. `https://portal.example.com` — **origin only**, no `/api/grading` suffix; we append it |

Both keys are static bearer-style secrets compared for exact equality. Rotate by agreeing a window in which both old and new are accepted.

## Direction 1 — the webhook

```
POST https://<SAHAHLY_API_BASE_URL>/api/grading/webhook
x-api-key: <webhook secret>
Content-Type: application/json
```

Call it once per student submission, as soon as the submission exists and its files are retrievable.

### Body

The submission object from the Postman collection, **plus an `assignment` object**:

```json
{
  "id": 54,
  "submission_date": "2026-06-18",
  "status": "Submitted",
  "grade": null,
  "marked": false,
  "mark_scheme": "https://files.example.com/cloud_file/5388?signature=…",
  "attachments": [
    "https://files.example.com/cloud_file/5389?signature=…"
  ],
  "assignment": {
    "id": 12,
    "name": "Unit 3 — Organic Chemistry",
    "grade": 50,
    "description": "Answer all questions. Show your working.",
    "due_date": "2026-06-20",
    "due_time": "23:59"
  }
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | number | **Required, non-null.** Your submission id. Stable and unique — it is our idempotency key. |
| `mark_scheme` | string (URL) | **Required, non-null on the webhook.** See below. |
| `attachments` | string[] (URL) | **Required, non-null.** `attachments[0]` is the student's work; see below. |
| `assignment` | object | **Required in practice.** See below. |
| `submission_date` | string | `YYYY-MM-DD`. |
| `status` | string | Free text, e.g. `Submitted` / `Marked`. Informational. |
| `grade` | number \| null | Null for an unmarked submission. |
| `marked` | boolean | `true` makes us record the submission as already graded and skip it. Send `false` for new submissions. |

### Four requirements that are easy to get wrong

**1. `assignment` is required in practice.** It is not part of the public submissions API shape, but the webhook must include it. `assignment.id` is what tells us which assignment a submission belongs to, and we need that to grade it — a submission that arrives without one cannot be graded. Include it on every webhook call, with a stable numeric `id` per assignment: the same assignment must always carry the same `id`.

**2. `mark_scheme` may NOT be null on the webhook.** A webhook whose `id`, `mark_scheme`, or `attachments` is `null` or absent is rejected with `400`. This is stricter than your `GET /submissions` endpoint, where a null `mark_scheme` is acceptable. If a submission has no mark scheme yet, do not send the webhook until it does — the mark scheme is what we grade against.

**3. Only `attachments[0]` is read.** The student's work must be the **first** element. Additional elements are ignored, so a multi-file submission must be merged into one PDF before you notify us.

**4. File URLs must be directly downloadable server-side.** Our server fetches `mark_scheme` and `attachments[0]` with a plain GET — no auth header, no cookie, no redirect to a login page. They must serve `Content-Type: application/pdf`. Pre-signed URLs are fine and expected; if the ones in the webhook expire, we re-fetch fresh ones from your API, which is why **both** `GET /api/grading/submissions` and `GET /api/grading/submissions/{id}` must mint new URLs on every call.

### Responses and retries

| Status | Meaning | What you should do |
|---|---|---|
| `200 {"received": true}` | Stored. | Nothing. Delivery is complete. |
| `400 {"message": "Missing required field(s): …"}` | A required field was null/absent. | Fix the payload. Retrying unchanged will fail identically. |
| `401 {"message": "Unauthorized"}` | Bad or missing `x-api-key`. | Check the webhook secret. |
| `5xx` | We failed to store it. | **Retry.** The payload is not saved. |

We write to our database *before* replying, so a `200` is a real durability guarantee rather than a bare acknowledgement — if we cannot store the submission you get a `5xx` and should re-deliver.

**Re-delivery is safe.** Records are keyed on `id` and re-delivering an existing submission will not overwrite one that is already being graded or has been graded. Please retry `5xx`s with backoff.

### Rejection examples

Exactly three fields are validated: `id`, `mark_scheme`, `attachments`. A field counts as missing if it is absent **or** explicitly `null` — `"mark_scheme": null` and omitting `mark_scheme` produce the same `400`.

**One field missing**

```http
POST /api/grading/webhook
x-api-key: <webhook secret>
Content-Type: application/json

{
  "id": 54,
  "submission_date": "2026-06-18",
  "mark_scheme": null,
  "attachments": ["https://files.example.com/cloud_file/5389?signature=…"]
}
```

```http
400 Bad Request

{ "message": "Missing required field(s): mark_scheme" }
```

**Several missing** — all of them are named in one response, comma-separated, always in the order `id`, `mark_scheme`, `attachments`. We do not stop at the first one, so a single call tells you everything to fix.

```http
POST /api/grading/webhook
x-api-key: <webhook secret>
Content-Type: application/json

{ "submission_date": "2026-06-18", "status": "Submitted" }
```

```http
400 Bad Request

{ "message": "Missing required field(s): id, mark_scheme, attachments" }
```

**Bad or missing key** — note the key is checked *before* the body. A request that is both mis-keyed and missing fields returns `401` and never mentions the fields; fix the key first, then expect to see any `400` on the retry.

```http
POST /api/grading/webhook
x-api-key: wrong-key
Content-Type: application/json

{ "submission_date": "2026-06-18" }
```

```http
401 Unauthorized

{ "message": "Unauthorized" }
```

**Storage failure** — the payload is *not* saved. Retry with backoff.

```http
500 Internal Server Error

{ "message": "Failed to persist submission" }
```

### Malformed payloads we accept anyway

These return `200` and are stored. Nothing will tell you at delivery time that they are wrong — they fail later, when we come to grade the submission, which is much harder to trace back. Please validate these on your side before sending.

| Payload | Why it passes | What actually happens |
|---|---|---|
| `"assignment"` omitted | We only validate `id` / `mark_scheme` / `attachments`. | Stored with `assignment: null`. We cannot tell which assignment it belongs to, so it **cannot be graded**. See requirement 1 above. |
| `"attachments": []` | An empty array is not `null`, so it passes the check. | Stored. There is no student work at `attachments[0]`, so we cannot grade it. |
| `"mark_scheme": ""` | An empty string is not `null`. | Stored. The mark-scheme download fails and we cannot grade it. |
| `"submission_date": "not-a-date"` | Presence is not checked and the value is not validated. | Stored with a null/invalid date. Does not affect grading, but the dashboard will sort it oddly. |

A numeric-string `id` such as `"54"` is fine — we coerce it to `54`, and it stays the same idempotency key as `54`. But an `id` that is not a number at all (`"abc"`, an object) is **not** fine, and fails in a misleading way:

```http
POST /api/grading/webhook
x-api-key: <webhook secret>
Content-Type: application/json

{ "id": "abc", "mark_scheme": "https://…", "attachments": ["https://…"] }
```

```http
500 Internal Server Error

{ "message": "Failed to persist submission" }
```

It passes the required-field check (`"abc"` is neither absent nor null), then fails when we write it to the database. You get a `5xx`, which the table above tells you to retry — **but this one will never succeed, no matter how many times you retry it.** It is a permanent failure wearing a temporary failure's status code. If a submission `5xx`s forever, check that `id` is a number before assuming the problem is on our side.

## Direction 2 — what we send back

Once we have graded the submission we call `POST /api/grading/submissions/{id}/marks` with `{ grade, comments, attachments }`. `comments` and `attachments` are **omitted entirely** when empty, so do not assume the keys are present.

**The annotated PDF URL expires after 7 days.** `attachments[0]` is a Cloudflare R2 pre-signed URL. Download the file and store your own copy when you handle the request. Do not hotlink it or save it verbatim — it will start returning `403` after a week.

## Go-live checklist

- [ ] You send us your API key and base URL; we send you the webhook secret.
- [ ] Your three endpoints match the Postman collection: exact field names, `{ "data": [...] }` envelope on the list, `filter[...]` params.
- [ ] `GET /submissions` returns **all** submissions in one response — not paginated, not capped.
- [ ] `GET /submissions` and `GET /submissions/{id}` both mint fresh pre-signed URLs on every call.
- [ ] `GET /submissions/{id}` returns `404` (not `500`) for an unknown id.
- [ ] Webhook fires on new submissions, includes `assignment`, and never sends a null `mark_scheme`.
- [ ] Webhook retries on `5xx`.
- [ ] Your `/marks` handler downloads and stores our annotated PDF rather than hotlinking it.
- [ ] End-to-end on staging: submit → webhook → appears in Sahahly → we grade the submission → grade and PDF land back on your side.
